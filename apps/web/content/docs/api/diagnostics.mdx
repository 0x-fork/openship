---
title: Error reporting
description: Correlate API failures and submit bounded browser diagnostics to your own instance.
---

Openship API responses include an `X-Request-ID`. Include this reference when reporting a failure. The
instance's structured logs associate it with the error category, operation, stack and authorized
resource identifiers where available. An incoming request ID is only a parent reference; each API
request receives a new server-generated ID.

Error reporting uses the same handler in Cloud, self-hosted installations and Desktop. The default
server destination is structured JSON on stderr. It does not require PostHog, Redis or a new database
table. Application logs, deployment logs and the security audit log keep their existing purposes.

## Browser reports

The dashboard automatically submits errors to its own instance. This endpoint is public so sign-in
and initialization failures can be reported. It cannot read logs or act on resources. Payloads cannot
assert a user, organization, severity or trusted API result, and every accepted event is marked
`untrusted` and redacted again by the server.

The body is an object with an `events` array of one to eight entries:

| Field | Limit | Meaning |
| --- | --- | --- |
| `name` | 80 characters | Error name; required. |
| `message` | 2,049 characters | Redacted message; required. |
| `component` | 1–160 characters | Optional source module label, such as `dashboard/hooks/useBuildConnection`; untrusted. |
| `stack` | 4,097 characters | Optional redacted stack. |
| `code` | 100 characters | Optional letters, digits, underscores, periods and hyphens. |
| `page` | 512 characters | Optional page path. Queries and invitation tokens are removed. |
| `requestId` | UUID | Optional parent API reference; not an identity. |
| `eventId` | 100 characters | Optional client reference; the server generates its own event and error IDs. |

Requests are limited to 64 KiB and 20 batches per minute per IP, including loopback requests. Extra
fields and invalid JSON are rejected with `400`, oversized bodies with `413`, and excess requests
with `429` and `Retry-After`. Accepted batches return `204` with `Cache-Control: no-store`.

During a Desktop connection to a remote instance, UI reports stay with the local instance. A remote
API records its own request failures with its authorized context. A UI report never inherits the
identity of an account selected after the error occurred.

Delivery is best effort with a bounded memory buffer. Reporting does not delay the operation while
waiting for an exporter. Buffer overflow and failed delivery produce explicit local diagnostic events;
process termination or loss of the local output can still lose events. This is not a durable audit log.
